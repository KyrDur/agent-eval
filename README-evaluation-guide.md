# 日志评测、日常检查与评测标准：新手使用说明

你已经让客服回答过一批问题。接下来通常有两个疑问：**这些回答好不好？给它打分的模型，判得可靠吗？**

“日志评测与日常运行”处理第一个问题；“评分标准”和“评测校准”处理第二个问题。这里的“日志”，就是之前保存的问题、回答、参考资料和执行记录。

## 先选对入口

| 你现在想做什么 | 使用哪里 | 会发生什么 |
| --- | --- | --- |
| 修改客服，让它重新回答，看有没有变好 | 主实验：初测 → 修改 → 复测 → 对比 | 产生新的客服回答，与原回答比较 |
| 检查之前已经生成的回答 | 日志评测与日常运行 | 读取原回答，核对资料，再评分 |
| 明确“什么算好回答” | 评分标准 | 定义每个分数的条件、例子和通过要求 |
| 检查评分模型是否误判 | 评测校准 | 将模型评分与独立人工判断对照，检查并修订评分方法 |

日志重评固定原回答。因此，改了评分规则后分数上涨，只能说明判分发生变化；要验证客服改好了，需要回主实验生成复测回答。

## 一、日志评测与日常运行

### 第一次使用，按这三步做

1. **选择回答。** 建立或选择“评测分类”，例如“售后政策问答”。在“从之前的评测导入”中选择一次已完成的初测或复测，点击“导入这次评测的回答”。不需要下载文件再上传。
2. **核对资料。** 系统带入原问题、原回答与当时保存的资料。逐条确认是否属于当前业务，以及参考资料能否判断这题。补上纳入或排除的理由，再保存本批回答。
3. **评分与复核。** 点击“开始评分已有回答”。查看判定、理由和引用；有异议时使用“人工复核本题”，说明依据。原模型判定与人工复核会分别保留。

导入只读取已保存的数据，不调用模型。只有开始评分、重试评分或启用每日评分计划时，才会发起相应模型请求。未执行的保留题不会随初测导入；仅做检索、没有保存回答的运行不能在这里评分。

### 为什么先核对资料？

比如用户问：“这个杯子多大、耐多少度、一盒几只？”

客服只检索到了退货规则，于是说“资料中没有规格，无法确认”。这时要分别看两件事：

- **有没有乱编？** 对照客服当时实际看到的检索资料判断。
- **有没有解决问题？** 对照这题完整的参考资料判断。如果完整资料明明有规格，客服却没有答出，任务仍可能不通过。

如果连完整参考资料也缺失，就可能只能标记“证据不足”。不能把资料不足直接计成通过，也不能仅凭一句“不知道”判定它在编造。

### 看到异常或不通过，下一步怎么分析？

先打开这一题，把原问题、原回答、当时检索到的资料和完整参考资料放在一起核对：

- 完整资料有答案，但没有检索出来：先检查资料切分、检索数量或排序。
- 已经检索到必要资料，回答却漏掉规格或例外：检查回答要求与模型是否正确使用资料。
- 原回答和依据都支持结论，评分理由却引用错误或漏看条件：先人工复核，再进入评分校准检查误判。
- 页面显示执行失败或评分未完成：先查看运行记录、连接与格式错误，不能把技术失败当作回答质量结论。

这些是排查方向，不能仅凭一题断定根因。主实验的本题结果页可以直接选择修改方式，查看原题与方案，确认、应用并复测；补充理由可选。「复制提问给 AI」会带入本题与拟改设置，请 AI 解释为什么值得试、有什么风险。

### 页面里的词是什么意思？

| 词语 | 含义与例子 |
| --- | --- |
| 评测分类／业务域 | 将不同业务分开评分。售后政策与商品推荐可能适用不同规则。 |
| 第 1 版、第 2 版 | 规则第几次保存。旧评测保留当时的版本，便于以后对照。 |
| 批次／冻结输入 | 本次一起检查的一组问题、原回答与资料。保存后形成固定版本；修订会另存新批次。 |
| 参考资料是否齐全 | 现有资料是否足以判断这道题。并非要求上传整个公司的全部资料。 |
| 对话历史 | 问这题之前聊过什么，用来理解“它”“上次”等说法。默认取最近 4 条用户和客服消息，也可选全部提供的历史。 |
| 同类问题分组 | 把同一类题放一起，例如“退货时限”，方便观察哪类题容易出错。 |
| 人工复核 | 人看过模型判定之后，再核对这一题。适合纠错和记录分歧。 |
| 评分校准 | 用事先独立完成的人工判断，检查模型是否按同样标准评分。 |

### 外部文件、字段映射与嵌套字段

这些功能保留在“导入外部文件或粘贴内容（可选）”里。只有要导入其他系统的数据时才需要；从本平台已有评测导入时不用配置。

**字段**就是一项信息，例如问题、回答。**字段映射**就是指定文件中的哪一列对应哪项信息。

例如，你的表格两列叫“客户提问”和“客服回复”：

| 页面设置 | 填什么 |
| --- | --- |
| 用户问题的原列名 | 客户提问 |
| 客服实际回答的原列名 | 客服回复 |

系统默认列名是 `question` 和 `answer`；文件已使用这些名称时留空即可。

**嵌套字段**是信息放在多层里面，例如：

```json
{"对话":{"问题":"能退货吗？"},"客服回复":"请提供订单信息。"}
```

问题放在“对话”里面，所以在“用户问题的原列名”填写 `对话.问题`。点号表示向里面找一层。普通表格直接填列名，不需要这种写法。

文件支持 CSV（表格）、JSON（一组记录）、JSONL（每行一条记录），每批 1–100 条，最多 5 MiB。完全重复的原记录会去重；同一问题的不同回答仍保留。预览发现问题时先修正，再保存。

### 结果怎么看？

先看“已判定多少题”，再看“判定的题里通过多少”。

例如 8 道参评题：3 道通过、4 道不通过、1 道证据不足。

- 判定覆盖：7 ÷ 8 = **87.5%**。
- 通过率：3 ÷ 7 = **42.9%**。

证据不足和执行失败不进入通过率分母，但必须在结果中保留；明确不适用的题不进入参评分母。如果运行还存在缺失或重复结果，页面不会发布整批通过率。看到高通过率时，也要检查覆盖范围，避免忽略没判出来的题。

### 每日检查会做什么？

每日计划在指定时间，使用当前模型重新评分**同一批已确认的回答**。适合观察固定题在不同时间是否出现判分变化。

目前不会自动接入每天新增的线上聊天。要检查新日志，需要先导入新批次，再更新计划。反复检查同一批题也不会增加独立样本数。执行需要服务在运行、模型连接有效，且受模型调用上限约束；密钥失效或服务重启后，需恢复模型连接。

## 二、评分标准与评测校准

### 评分标准：先说明什么算好

当前初始规则将回答分为四个维度，每项通常为 0、1、2 分。它是一套起点，需要结合具体业务验证。

| 维度 | 0 分 | 1 分 | 2 分 |
| --- | --- | --- | --- |
| 事实与依据 | 与规则冲突或无依据承诺 | 部分关键表述缺少支持 | 关键事实有支持，限制准确 |
| 条件覆盖 | 漏掉会改变结论的条件 | 主问题已答，漏了次要子问题 | 必要条件与子问题都覆盖 |
| 意图与相关性 | 答非所问 | 主要相关，但明显跑题扩展 | 直接回应，必要时合理追问 |
| 下一步可用性 | 操作错误或无法执行 | 基本能用，但缺少信息 | 用户可以据此行动 |

初始通过要求：前两项至少 2 分，后两项至少 1 分；存在关键错误则不通过。纯事实题无需操作步骤时，“下一步可用性”可标为不适用，并说明理由。缺少判定需要的依据时，应保留证据不足状态。

例如“定制商品可以七天无理由退货吗？”：如果规则写明定制商品例外，却回答“所有商品都能退”，这属于关键条件遗漏或政策冲突，不能靠其他维度的高分抵消。

**评分标准**规定什么算好；**评分模型的要求／提示词**告诉模型怎样应用标准、怎样引用依据。这两个部分都可以修订，但修改版本后要重新检查判分可靠性。

### 评测校准：检查打分的人是否可靠

模型也会误判，例如忽略例外、偏好长回答、把没解决问题与编造事实混为一谈。校准就是用人工参照把这些问题找出来。

1. 选定一组固定的问题、原回答和当时资料。
2. 人先按评分细则独立判断，处理人工之间的分歧，保存依据。
3. 让评分模型判同一批回答，对照误判、漏判和证据不足情况。
4. 根据问题修订评分规则或评分要求，在校准题上比较版本。
5. 用之前未参与调试的保留题做最终检查，报告适用范围与限制。

如果已经看过模型答案再做人评，那是复核，不能当作独立盲评。它仍有纠错价值，但不能据此证明评分模型与独立人工高度一致。页面提供这些流程，不代表系统已经完成真实人工校准。

### 我现在需要用哪一部分？

第一次做项目，先完成主实验的初测、一次修改和复测，学会看逐题证据。想检查已有回答时，用日志评测；开始怀疑“为什么这一题判错了”时，再进入评分标准与评测校准。每日计划可以等有固定题集、明确检查目的之后再启用。
